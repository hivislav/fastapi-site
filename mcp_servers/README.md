# Локальные MCP-серверы проекта

Пять серверов [MCP](https://modelcontextprotocol.io) (Model Context Protocol) на
официальном SDK `@modelcontextprotocol/sdk`. Три из них **бесплатные и без
ключей** (регистрация и API-токены не нужны, интернет требуется только в момент
вызова инструмента), а `git` и `support` вообще не ходят в сеть: первый читает
рабочую копию самого проекта, второй — JSON обращений поддержки.

| id | Название | Что даёт | Источник данных |
|---|---|---|---|
| `weather` | Погода | текущая погода и прогноз по дням для любого города | 7timer.info (NOAA GFS) + геокодер Open-Meteo |
| `currency` | Курсы валют | официальные курсы Банка России к рублю, перевод суммы, список курсов | cbr.ru |
| `crypto` | Криптовалюты | цены монет в обычных валютах, обзор рынка (капитализация, изменение за сутки и неделю) | CoinGecko |
| `git` | Git-репозиторий проекта | текущая ветка, последний коммит, список файлов, изменения (diff), история коммитов и содержимое файла | рабочая копия этого проекта (`git`) |
| `support` | Поддержка: клиенты и обращения | обращения по работе с этой кодовой базой: тема, статус, приоритет, продукт, описание со слов клиента, переписка; клиент — имя и id | локальный JSON проекта (`data/tickets.json`) |

> Свои серверы проекта — `open_meteo` (погода, прогноз, качество воздуха,
> координаты) и `city_registry` (реестр городов и жителей) — здесь **не лежат**:
> это серверы `open-meteo-mcp` и `city-registry-mcp`, развёрнутые на VPS. В
> каталоге `mcp_servers/` только локальные процессы; удалённые серверы
> подключаются по Streamable HTTP через SSH-туннель, а их адреса и токены задают
> переменные `OPEN_METEO_MCP_URL` / `OPEN_METEO_MCP_TOKEN` и
> `CITY_REGISTRY_MCP_URL` / `CITY_REGISTRY_MCP_TOKEN` в `.env`.

## Как это работает

Приложение (`app/ai/mcp.py`) — клиент MCP с двумя транспортами: локальные
серверы оно запускает отдельным процессом и общается по **stdio** на языке
JSON-RPC 2.0 (`initialize` → `tools/list` → `tools/call`), а удалённые серверы
вызывает HTTP-запросом (Streamable HTTP). Сервер объявляет инструменты, а агент
вызывает их сам, когда для ответа не хватает фактов.

Включение — по кнопке **«MCP»** рядом с шестерёнкой проекта: галочки серверов и
«применить». Набор серверов — настройка ПРОЕКТА (`task["mcp"]`): включённые
серверы агент видит в каждом запросе, выключенные не запускаются вовсе.

## Сервер `git`: агент, ассистент разработчика и AI-ревью

`git.mjs` даёт агенту то, чего у модели нет вовсе, — состояние рабочей копии
проекта и изменения ветки. Семь инструментов, все **только на чтение**:

| инструмент | что отвечает |
|---|---|
| `git_status` | ветка, последний коммит, отслеживаемая ветка (впереди/отстала), изменённые файлы |
| `git_files` | файлы проекта (все или только изменённые), можно ограничить каталогом |
| `git_diff` | сами изменения: `working`, `staged`, `head` или `branch` (с базовой веткой), плюс `stat_only` |
| `git_branch_files` | изменённые файлы **ВЕТКИ против базовой** (не рабочей копии!): статус и `±строки` — то, что проверяет ревью и pull request |
| `git_branch_diff` | diff ветки против базовой **окнами по строкам**: «строки 1–120 из 5567; дальше `from_line=121`» — целиком большой diff в ответ не влезает |
| `git_log` | последние коммиты ветки (хеш, дата, автор, тема) |
| `git_show_file` | содержимое файла с номерами строк — рабочей копии или версии из ветки/коммита |

**Пустой `git_diff` — с разными причинами, и их называет сервер.** У НЕотслеживаемого файла (нового, `??`) diff пуст потому, что сравнивать не с чем — у него нет ни одной версии в истории; у игнорируемого — потому что git его не ведёт; у файла с правками только в индексе — с подсказкой «повтори со `scope=staged`»; у отслеживаемого и чистого — честное «изменений нет». Пустой diff без пути дополнительно называет новые файлы: их diff не показывается вовсе. Та же логика у `git_log`: «коммитов нет» у нового файла означает «истории не существует», а не «файл не менялся».

**Зачем два инструмента про ветку, если есть `git_diff`.** `git_diff` показывает
РАБОЧУЮ КОПИЮ: в CI (pull request) она чистая, и ревью увидело бы пустоту. Плюс
ответ инструмента ограничен 4000 символами у клиента и 3400 у сервера — большой
pull request физически не влезает в один вызов, поэтому `git_branch_diff` режет
diff по строкам и сам говорит, откуда продолжать.

Запись в репозиторий через этот сервер **невозможна**: выполняются только
читающие команды, аргументы уходят в git списком (`execFile`, без оболочки),
`GIT_OPTIONAL_LOCKS=0` не даёт даже `status` обновлять индекс. Пути проверяются:
выход за корень репозитория, каталоги `.git/`, `data/`, `venv/`, `node_modules/` и
файлы с секретами (`.env`, ключи) закрыты. Ответы держатся в бюджете 3400
символов (клиент берёт не больше 4000) и честно говорят, что показано не всё.

Каталог репозитория — корень проекта; другой задаёт переменная `GIT_REPO_DIR`
(см. `.env.example`).

С этим сервером работает **команда `/help` в чате** — ассистент разработчика:
вопросы о самом проекте («как устроен поиск по базам знаний», «что делает
`app/ai/mcp.py`», «что изменилось в этой ветке»). Ответ строится по документации
проекта (базы знаний, кнопка «RAG») и по состоянию репозитория из этого сервера,
под ответом — источники с цитатами и переходом к чанку. Команда идёт мимо
пайплайна задачи: ни плана, ни шагов, ни автомата. Если вопрос про клиента или
Данных обращений клиентов здесь НЕТ: поддержка — отдельная команда `/support`
(см. ниже), и в `/help` инструменты сервера `support` не подключаются.

И **команда `/ai_review`** — AI-ревью изменений ветки: потенциальные баги,
архитектурные проблемы, рекомендации. Изменения и список файлов приходят от этого
же сервера (`git_status`, `git_branch_files`, `git_branch_diff` — ветка против
базовой, окнами по строкам), документация и код — из баз знаний проекта и
репозитория. Режим включается и выключается командами `/ai_review_enable` и
`/ai_review_disable`. Тот же разбор делает пайплайн на pull request
(`.github/workflows/ai-review.yml` → `tools/ai_review.py`); там репозиторий
подключается этой же переменной `GIT_REPO_DIR`, а зависимости сервера ставятся
шагом `npm ci --prefix mcp_servers`.

## Сервер `support`: клиенты и обращения (ассистент поддержки)

`tickets.mjs` даёт то, чего у модели нет вовсе, — данные ОБРАЩЕНИЯ конкретного
человека по работе с ЭТОЙ кодовой базой. Базы знаний отвечают, «как устроен
продукт», а на вопрос «почему не работает вход?» нужны факты обращения: что
человек делал и что ему уже отвечали. Клиент здесь — просто имя (и id): тарифа,
компании и почты в этом проекте нет, и выдумывать их сервер не станет.

**ДОСТУПЕН ТОЛЬКО ПО КОМАНДЕ.** В записи реестра у сервера стоит `command:
"/support"` — значит, в запросах агента его инструментов нет вовсе
(`mcp_store.agent_enabled` отсекает командные серверы): иначе на обычный вопрос
«почему не работает авторизация?» агент отвечал бы по переписке случайного
клиента. Открывает их команда `/support [номер обращения] <вопрос>`
(`app/ai/support.py`, маршрут `POST /api/agent/support`), и она же — единственное
место, где обращение можно завести или дописать. Семь инструментов:

| инструмент | что отвечает | меняет данные |
|---|---|---|
| `list_users` | клиенты поддержки: имя, id, сколько у кого обращений | нет |
| `get_user` | карточка клиента (имя, id) и список его обращений | нет |
| `search_tickets` | обращения по СЛОВАМ ЗАПРОСА — тема, описание, переписка, продукт, имя клиента | нет |
| `get_ticket` | одно обращение целиком: статус, приоритет, дата, описание со слов клиента, ВСЯ переписка и данные клиента | нет |
| `list_tickets` | обращения списком: все, по клиенту, по статусу | нет |
| `create_ticket` | завести обращение: номер, тема, описание со слов клиента, заявитель; клиент находится по имени или заводится | **да** |
| `add_comment` | сообщение в переписку обращения | **да** |

**Заявителя называет КОД, а не модель.** В приложении профиль — это клиент, и имя
берётся из его поля «Имя»: веб-слой подставляет значение в аргумент `requester`
перед самым вызовом (`app/routers/chat.py`, `_fill_requester`; механизм — общий
дополнитель аргументов, `app/ai/mcp.py`, `ARG_FILLERS`). Модель заявителя не
выбирает — как не она ставит флаг перезаписи: личность, придуманная моделью,
попала бы в чужое обращение. Уже названного человеком заявителя код НЕ перебивает
(«заведи обращение для Дмитрия Ковалёва» — законная просьба), а пустое имя в
профиле не подставляется вовсе: сервер честно ответит, что заявитель не назван.

**Дубликаты не плодятся молча.** Перед созданием сервер ищет похожие ОТКРЫТЫЕ
обращения (совпадение значимых слов темы или описания) и без `force=true` второе
не заводит — показывает найденное и предлагает либо дописать в него
(`add_comment`), либо подтвердить создание. Закрытые обращения («решён»,
«закрыт») дубликатом не считаются: повторная жалоба по той же теме — это новое
обращение. Номер следующий за максимальным (`TCK-1043`), а не «количество + 1»:
в файл кладут данные руками, и нумерация по счётчику выдала бы занятый номер.

**Данные — ЛОКАЛЬНЫЙ JSON, а не CRM и не сеть.** По умолчанию `data/tickets.json`
(путь переопределяет `TICKETS_FILE`); структура — `users` и `tickets` с полями
`id`, `name` у клиента и `id`,
`user_id`, `subject`, `status`, `priority`, `product`, `created_at`,
`updated_at`, `description`, `comments[{author, at, text}]` у обращения. Каталог
`data/` в git не хранится, поэтому демонстрационные данные лежат в репозитории
отдельно — `tickets.seed.json`, — и первый же вызов создаёт рабочий файл из этого
образца: сервер работает сразу после `npm install`, без настройки и ключей. Свой
файл кладут на это место как есть.

**Почему поиск, а не только номер.** Человек спрашивает словами заявителя и
номера не знает: `search_tickets` ищет по теме, описанию, переписке, продукту и
имени клиента, а служебные слова запроса («почему», «не», «как») отбрасываются —
без этого «почему не работает авторизация?» находило пять обращений, где
совпадало одно слово «не». Слабые совпадения (только в переписке — «спасибо,
помогло» из закрытого обращения) в выдачу не идут. Номер без префикса («1041»)
разрешается, если он однозначен.

**Статусы и группы.** Кроме точных статусов (`новый`, `в работе`, `ждём ответа`, `решён`, `закрыт`) сервер понимает ГРУППЫ и мягкие формы: «открыто/открытые/активные/незакрытые» — это всё, что ещё не закончено (`новый` + `в работе` + `ждём ответа`), «закрытые/решённые» — `решён` + `закрыт`. Значения-синонимы приводятся к каноническим («high» → `высокий`, «in progress» → `в работе`), а нераспознанное называется причиной со списком допустимых. Живой случай 14.10: на «/support — что у нас в работе» диспетчер прислал статус «открыто», строгая схема отклонила вызов, и режим вместо списка просил человека выбрать статус.

**Честность важнее полноты.** Ничего не найдено — сервер отвечает ОТКАЗОМ и
называет, по чему искал и что вообще есть в базе (сколько обращений, какие
статусы, последние номера): пустой ответ модель достраивает догадкой, и человек
получает выдуманный статус. Ответы держатся в бюджете 3000 символов (клиент
берёт не больше 4000) и говорят, что показано не всё.

**Запись — два инструмента из семи, и оба отложены.** Имена `create_ticket` и
`add_comment` начинаются с `create_` и `add_`, поэтому клиент агента сам считает вызов создающим результат
(`RESULT_RE` в `app/ai/mcp.py`) и не выполняет его до подтверждения плана.
Испорченный файл данных НЕ перезаписывается: чтение падает с причиной, запись
отменяется, содержимое остаётся прежним.

**Как работает команда `/support`** (`app/ai/support.py`):

* `/support TCK-1041 почему не работает вход?` — выбранное обращение читает КОД
  (номер назвал человек, диспетчера спрашивать не о чем), обращение приходит
  вместе с карточкой клиента; модель получает ТОЛЬКО это обращение, ПРОФИЛЬ
  КЛИЕНТА (его стиль общения, формат ответа и ограничения — решение 15.10),
  документацию продукта и вопрос — ни истории разговора, ни памяти задачи в
  промпт не попадает;
* `/support TCK-1041` — то же, но вопрос по умолчанию: что известно, что сделали,
  что дальше;
* **неизвестный номер и сбой сервера останавливают запрос ДО ВЫЗОВА МОДЕЛИ**:
  ответ по несуществующему обращению — либо выдумка, либо общие слова
  документации, и платить за него вызовом модели незачем;
* `/support <вопрос>` без номера — набор вызовов выбирает диспетчер, но ТОЛЬКО
  среди инструментов этого сервера (`support.filter_calls`), и изменения
  (завести обращение, ответить клиенту) выполняются лишь по ПРЯМОЙ ПРОСЬБЕ
  человека (слова «заведи», «запиши», «ответь клиенту»): иначе модель «на всякий
  случай» дописала бы клиенту ответ, которого никто не поручал;
* ответ строится по-поддержке: что случилось у клиента, что уже сделали, что
  делать дальше, а механика продукта — из документации со ссылками на фрагменты;
  выдумывать статусы, даты и ответы поддержки промпт запрещает.


**Готовый демо-проект** — `./venv/bin/python tools/support_demo.py`: создаёт
проект с включёнными сервером `support` и базой знаний продукта (приложение при
этом должно быть остановлено — работающее держит workspace в памяти). Дальше
вопрос «почему не работает авторизация?» в этом проекте отвечается с учётом
данных обращения.

## Установка

Серверам нужен Node.js (18+) и один раз установленные зависимости:

```bash
cd mcp_servers
npm install
```

Каталог `node_modules/` в git не хранится (он большой). Если он отсутствует,
диалог «MCP» в приложении покажет у серверов причину «не установлен MCP SDK:
выполните npm install в каталоге mcp_servers» — инструменты при этом просто не
подключаются, остальное приложение работает как обычно.

Путь к Node.js можно задать переменной окружения `MCP_NODE_BIN`, каталог
серверов — `MCP_SERVERS_DIR` (см. `.env.example`).

```bash
# список инструментов и вызов (сервер отвечает на stdin/stdout, лог — в stderr)
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"cli","version":"1"}}}' \
  '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' \
  '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"get_weather","arguments":{"city":"Москва"}}}' \
  | node weather.mjs

# сервер проекта: ветка и изменения
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"cli","version":"1"}}}' \
  '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"git_status","arguments":{}}}' \
  | node git.mjs

# сервер поддержки: обращение по словам вопроса (файл данных — свой, чтобы не
# трогать рабочий: TICKETS_FILE=... node tickets.mjs)
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"cli","version":"1"}}}' \
  '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"search_tickets","arguments":{"query":"почему не работает авторизация?"}}}' \
  | node tickets.mjs
```

Автоматические проверки: `./venv/bin/python tools/check_mcp.py` (клиент, маршруты
и работа MCP в диалоге агента — без сети и без Node),
`./venv/bin/python tools/check_dev_help.py` (инструменты `git` на настоящем
временном репозитории, охрана путей, команда `/help` — тоже без сети) и
`./venv/bin/python tools/check_support_mcp.py` (сервер `support` целиком на
временном файле данных: поиск обращения по вопросу клиента, чтение обращения,
создание обращения, запись комментария, отказ вместо выдумки, испорченный файл не
перезаписывается; правила команды `/support` — разбор, отсечки вызовов и промпт;
отсечка командного сервера от агента; маршрут на заглушке модели — выбранное
обращение, остановка до модели на неизвестном номере, подстановка заявителя,
изменения только по просьбе).

## Свой сервер

Добавьте запись в `SERVERS` (`app/ai/mcp.py`): `id`, `name`, краткое
`description` для интерфейса, `source` и либо `script` (файл в этом каталоге,
запускается через `node`), либо готовую `command` — тогда подойдёт ЛЮБОЙ
MCP-сервер, включая сторонний на Python или npx. Протокол клиента от SDK не
